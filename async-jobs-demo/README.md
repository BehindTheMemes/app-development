# Асинхронная обработка задач через RabbitMQ

Демонстрационный проект из трёх контейнеров: API-сервис A, обработчик B и RabbitMQ с Management UI. Сервисы не вызывают друг друга напрямую — обмен происходит только через брокер сообщений.

## Архитектура

```text
Клиент
  |
  | POST /jobs
  v
Сервис A (FastAPI) -- publish --> очередь tasks
                                      |
                                      v
                                Сервис B (worker)
                                      |
                              обработка 2,5 секунды
                                      |
                             publish JobCompleted
                                      v
Сервис A (consumer) <-- очередь results
  |
  | GET /jobs/{id}
  v
Клиент получает DONE + result
```

| Компонент | Назначение |
|---|---|
| `api` (порт `8000`) | Принимает задачи, хранит их состояние в памяти и читает события из `results` |
| `worker` | Читает `tasks`, имитирует обработку 2,5 секунды и публикует `JobCompleted` в `results` |
| `rabbitmq` | Брокер сообщений и веб-интерфейс управления |
| `tasks` | Очередь команд: A → B |
| `results` | Очередь событий-фактов: B → A |

Обе очереди объявляются как durable. Публикуемые сообщения имеют `delivery_mode=2` (persistent). Для публикаций включены publisher confirms.

## Требования

- Docker Desktop или Docker Engine с плагином Docker Compose.
- Свободные порты `8000`, `5672` и `15672`.

Python локально устанавливать не нужно: зависимости устанавливаются при сборке Docker-образов.

## Запуск

Из корневой папки проекта выполните одну команду:

```bash
docker compose up --build -d
```

Проверить состояние контейнеров:

```bash
docker compose ps
```

API будет доступно по адресу <http://localhost:8000>, Swagger UI — <http://localhost:8000/docs>.

RabbitMQ Management UI: <http://localhost:15672>

- Логин: `appuser`
- Пароль: `apppass`

В разделе **Queues and Streams** должны отображаться очереди `tasks` и `results`. В момент обработки можно увидеть, как сообщение появляется в `tasks`, а после обработки событие публикуется в `results`. Поскольку сервис A быстро читает `results`, счётчик сообщений в этой очереди обычно возвращается к нулю.

## Проверка API: POST → ожидание → GET

### Вариант для Windows PowerShell

Создать задачу:

```powershell
$job = Invoke-RestMethod -Method Post `
  -Uri http://localhost:8000/jobs `
  -ContentType "application/json" `
  -Body '{"topic":"Подготовить отчёт по проекту"}'

$job | ConvertTo-Json
```

Пример ответа — HTTP `202 Accepted`:

```json
{
  "id": "f2d7e7d8-58b2-4c8f-9b3d-2a41d1041a5a",
  "status": "ACCEPTED"
}
```

Сохранить идентификатор, подождать около трёх секунд и запросить статус:

```powershell
$id = $job.id
Start-Sleep -Seconds 3
Invoke-RestMethod -Uri "http://localhost:8000/jobs/$id" | ConvertTo-Json
```

Ожидаемый результат:

```json
{
  "id": "f2d7e7d8-58b2-4c8f-9b3d-2a41d1041a5a",
  "status": "DONE",
  "result": "Задача «Подготовить отчёт по проекту» выполнена",
  "completedAt": "2026-11-26T16:20:03.123456+00:00"
}
```

UUID и время в фактическом ответе будут другими. Если запросить статус сразу после POST, обычно вернётся `ACCEPTED`; после завершения обработки — `DONE` с результатом.

### Вариант для Bash

```bash
JOB=$(curl -s -X POST http://localhost:8000/jobs \
  -H 'Content-Type: application/json' \
  -d '{"topic":"Подготовить отчёт по проекту"}')

echo "$JOB"
ID=$(echo "$JOB" | python -c 'import json,sys; print(json.load(sys.stdin)["id"])')
sleep 3
curl -s "http://localhost:8000/jobs/$ID"
```

## Почему POST отвечает 202 Accepted

HTTP `202 Accepted` означает, что запрос принят для последующей обработки, но сама работа ещё не завершена. Сервис A создаёт идентификатор, публикует задачу в `tasks` и возвращает клиенту `id` и `ACCEPTED`, не ожидая завершения работы B. Это позволяет не удерживать HTTP-соединение открытым в течение всей длительной операции. Результат клиент получает отдельным запросом `GET /jobs/{id}`.

Публикация в RabbitMQ подтверждается брокером до отправки ответа. Если брокер недоступен или не подтверждает публикацию, API вернёт `503 Service Unavailable`, а не успешный `202`.

## Что происходит при сбое B и какая гарантия доставки

В проекте реализована семантика **at-least-once** для обработки сообщений:

1. B получает сообщение с `auto_ack=False`, то есть RabbitMQ не считает его обработанным автоматически.
2. B выполняет работу и сохраняет сформированное событие в файл `/data/processed_jobs.json`.
3. B публикует `JobCompleted` в `results` с persistent delivery и ждёт publisher confirm от RabbitMQ.
4. Только после подтверждения публикации B отправляет `ack` исходному сообщению из `tasks`.

Если B упадёт до `ack`, RabbitMQ после закрытия соединения вернёт неподтверждённое сообщение в очередь и доставит его снова. Это предотвращает потерю сообщения из-за преждевременного подтверждения. Однако at-least-once допускает повторную доставку — это не exactly-once.

### Защита от дублей

- В B используется `id` задачи как ключ идемпотентности. Результат сохраняется в JSON-файл на отдельном Docker volume **до** публикации события. При повторной доставке B использует сохранённый результат, а не запускает задержку и обработку заново.
- Сервис A обновляет состояние задачи по тому же `id`. Повторное событие `JobCompleted` устанавливает то же состояние `DONE`, а не создаёт вторую задачу. Поэтому повторная доставка результата не приводит к повторному изменению состояния.
- Если B завершится после публикации `JobCompleted`, но до `ack`, результат может быть опубликован повторно. Это нормальное поведение at-least-once; A обрабатывает такой дубль идемпотентно.

Ограничение демонстрационного решения: если B аварийно завершится посреди самой функции обработки, до сохранения результата в файл, заглушка будет запущена повторно после redelivery. Здесь это безопасно, потому что обработка только ждёт и формирует строку результата. Для реального побочного действия (например, списания денег или создания заказа) нужна идемпотентность на стороне операции или надёжное хранилище обработанных ключей; одной памяти процесса недостаточно.

## Важные ограничения демонстрации

- По условию задачи сервис A хранит статусы и результаты в памяти. После перезапуска A его словарь задач очищается; RabbitMQ при этом сохраняет свои durable-очереди и сообщения. Для сохранения статусов между перезапусками A потребовалось бы постоянное хранилище, но в этом задании оно намеренно не используется.
- Файл кэша B хранится в Docker volume `worker_data` и переживает пересоздание контейнера. Он нужен для демонстрации идемпотентности, это не база данных.
- В учебном проекте нет dead-letter queue и политики ограниченного числа повторов: сообщение с ошибкой повторно ставится в очередь. В промышленном сервисе следует добавить DLQ, мониторинг и стратегию обработки poison messages.
